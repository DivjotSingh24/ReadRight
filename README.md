# ReadRight

**A patient reading coach that listens to a child read aloud, catches exactly where they stumble, and helps them sound it out — one word at a time.**

🔗 **Live demo:** https://read-right-eta.vercel.app/
*(Best experienced in Chrome or Edge with a microphone.)*

---

## The problem

Learning to read out loud is one of the highest-leverage moments in a child's education — and one of the hardest to support at scale. Measuring a child's *oral reading fluency* (which words they get, which they skip, where they self-correct) traditionally requires a teacher or tutor sitting one-on-one with them, listening. There simply aren't enough of those hours to go around.

Most reading apps sidestep this. They quiz kids on words with taps and multiple choice, but they never actually *listen* to a child read. ReadRight is an attempt at the harder, more useful thing: a coach that hears the child read a real sentence, notices the specific word they got stuck on, and gently helps them through it — the way a patient tutor would.

## What it does

- **Listens as the child reads a sentence aloud** using in-browser speech recognition.
- **Grades each word** and colors the sentence live: green (got it), amber (close), red (needs another try).
- **Coaches missed words out loud**, one at a time, in a warm, encouraging voice — sounding the word out phonetically ("That word starts with an *h* sound... h-op... hop!").
- **Adapts difficulty automatically.** Read well and the app moves you up a level with a warm, spoken celebration; struggle and it gently eases off to an easier story — honestly acknowledging that one was tricky, never with any sense of failure.
- **Speaks to the child like a person.** Every message reflects how they actually read, in warm, simple language, and is spoken aloud — because a five-year-old can't read the encouragement meant to help them read.

## The interesting engineering problem: forgiving the recognizer without forgiving the reader

Browser speech recognition is noisy. It routinely mishears a *correctly read* word — a child says "boat" and the recognizer transcribes "board", or "hop" comes back as "hope". A naive app that compares the transcript to the expected text character-for-character would punish a child who read perfectly, which is both wrong and demoralizing.

But you can't simply forgive everything, or you'd miss the real misreads the coach exists to catch.

ReadRight handles this with a **phonetic tolerance layer**:

- Expected and spoken words are aligned in order using word-level edit distance, so a single skipped word is flagged on its own rather than knocking every following word out of alignment.
- Each word is then judged not on exact spelling but on **phonetic closeness** (after a light spelling-to-sound normalization), with a same-first-sound guard. This forgives the recognizer's near-misses ("board" for "boat") while still catching genuine reading errors ("hat" read as "cat").
- The tolerance threshold is a single tunable constant, so the trade-off between "too forgiving" (misses real errors) and "too strict" (punishes correct reading) can be dialed in.

This trade-off is the heart of the app, and getting it right — never coaching a word the child read correctly, while still catching clear misreads — is what makes the coaching feel trustworthy rather than random.

## Architecture

The app is deliberately simple and almost entirely client-side:

- **Frontend (browser):** Next.js + React + TypeScript + Tailwind. Handles the story UI, speech recognition (Web Speech API), the word-matching/grading logic, level progression, and reading messages aloud via the browser's speech synthesis.
- **One serverless function (`/api/coach`):** the *only* server-side code. It exists solely so the AI API key never reaches the browser. It takes the missed word and returns a short, warm, phonics-based hint.
- **AI coaching:** the hint text is generated by the Gemini API, with a **local phonics fallback** — if the API is unavailable, rate-limited, or errors for any reason, the app falls back to a locally-generated hint so the coach *always* speaks. The response reports which source produced the hint, so a silent fallback is impossible to miss.

There is no database and no separate backend server. Story content is authored and leveled by hand for reliability and to keep the phonics coaching free of ambiguous words.

## Tech stack

- **Next.js** (App Router) + **React** + **TypeScript**
- **Tailwind CSS**
- **Web Speech API** — speech recognition (listening) and speech synthesis (speaking), both in-browser
- **Gemini API** — coaching hints, with a local fallback
- Deployed on **Vercel**

## Running locally

```bash
# 1. Install dependencies
npm install

# 2. Add your Gemini API key
#    Create a file named .env.local in the project root:
echo "GEMINI_API_KEY=your-key-here" > .env.local

# 3. Run the dev server
npm run dev
```

Then open http://localhost:3000 in **Chrome or Edge** (the Web Speech API is not supported in Firefox or Safari) and allow microphone access.

Without a key, the app still runs — every hint comes from the local phonics fallback.

## Design decisions worth noting

- **Authored stories, not AI-generated content (for now).** For early readers, vocabulary level and pronunciation clarity matter enormously. Hand-authored, hand-leveled stories guarantee every word is age-appropriate and free of heteronyms ("wind", "read", "bow") that would confuse phonetic sounding-out. (See the roadmap for how AI generation fits in safely.)
- **Auto-stop on silence, tuned for early readers.** The mic stops on its own when the child finishes — but only once they've reached the end of the sentence, so a child pausing mid-sentence to sound out a hard word is never cut off.
- **Graceful degradation everywhere.** No microphone support, no API key, a failed API call — each has a sensible fallback so the experience never simply breaks.

## Roadmap: where the AI goes next

Today's build focuses on getting the *hard foundation* right — really listening to a child read, judging it fairly despite a noisy recognizer, and responding like a warm human. That foundation is what makes the following AI directions possible and genuinely useful, rather than gimmicks bolted onto a demo.

**1. Miscue-aware, personalized coaching.**
Right now hints sound out the missed word. The natural next step is to feed the AI the *pattern* of a child's errors over time — do they consistently drop word endings? Confuse short vowels? Struggle with consonant blends? — and have it generate coaching targeted at that child's specific, recurring difficulty, the way a reading specialist would. The data (which words, misheard as what, how often) is already captured by the grading layer.

**2. AI-generated stories at exactly the child's level.**
Instead of a fixed library, generate fresh, endless stories calibrated to the child's *current* reading level and interests (dinosaurs, space, football), constrained by a controlled vocabulary list so every word is one they can actually attempt. The reliability challenge — making sure generated text stays within a target reading level and avoids ambiguous words — is real, which is exactly why the current version uses authored content as a proven baseline first.

**3. A true pronunciation model, beyond the browser recognizer.**
The browser's Web Speech API is convenient but blunt, and it wasn't built for children's voices. A dedicated speech model (or a phoneme-level pronunciation-assessment API) would let ReadRight hear *how* a word was pronounced, not just guess which word it was — enabling real feedback on specific sounds ("your *th* sounded like *f*"), which is where the biggest reading gains for young learners actually live.

**4. Comprehension, not just decoding.**
Reading words correctly isn't the same as understanding them. AI-generated, level-appropriate comprehension questions after each story ("Why was Pam happy?") would let ReadRight coach *understanding* alongside fluency — the difference between word-calling and real reading.

**5. A dashboard for parents and teachers.**
Because every reading session already produces structured data (words attempted, accuracy, words that needed coaching, level progression), that data can roll up into a simple view of a child's growth over time — the kind of running record a teacher keeps, generated automatically. AI can summarize it in plain language: "This week Bilal is much stronger on blends but still finds silent-*e* words tricky."

**6. Multilingual and accessibility support.**
The same architecture extends to other languages and to learners with different needs — larger text, dyslexia-friendly fonts, adjustable pacing — widening who the coach can help.

## Limitations & honest caveats

- Browser speech recognition accuracy varies by microphone, accent, and especially by children's voices; the phonetic tolerance layer mitigates this but cannot eliminate it. (Addressing this properly is roadmap item 3.)
- The Web Speech API requires Chrome or Edge.
- There is a short delay (typically 1–2 seconds) before a spoken hint, from the round trip to the AI. The local fallback is near-instant.
